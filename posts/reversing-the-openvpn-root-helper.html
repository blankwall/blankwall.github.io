Part 2: Reversing the OpenVPN Root Helper

November 20, 2026

In Part 1, I found OpenVPN's ovpnhelper running as root under PID 647 and confirmed that my normal user account could connect to /var/run/ovpnhelper_service.sock. Connecting did not prove there was a bug. Next I needed to see what the helper actually did, how clients talked to it, and whether it checked who was connecting.

Test Environment

This analysis was performed on the same Apple Silicon Mac running macOS 15.3 (build 24D60), with OpenVPN Connect 3.6.0 (build 5410) installed. I analyzed /Library/Frameworks/OVPNHelper.framework/Versions/Current/usr/sbin/ovpnhelper (SHA-256: 286271935efeaeac715c5ddd285b170cfdd23386c990983e2832074af00d9ea2) with angr 10.0.5, and also looked statically at the ARM64 helper from OpenVPN Connect 3.8.2 (build 6009) for comparison.

Checking Symbols

Many release binaries strip function names before shipping, leaving only raw addresses. Before loading a decompiler, I ran nm to see if readable C++ symbols were still in the binary.

nm --demangle /Library/Frameworks/OVPNHelper.framework/Versions/Current/usr/sbin/ovpnhelper \
  | grep -E "allow_client|GetRoutes|ListApps|DPCRequestHandler|callToRpc|execCommand"
00000001000329cc t ServerListener::allow_client(openvpn::AsioPolySock::Base&)
000000010000797c T GetRoutes()
000000010000c4c0 t ListAppsHandler::process(...)
000000010000db9c t DPCRequestHandler::DPCRequestHandler()
000000010000e330 t DPCRequestHandler::process(...)
0000000100007240 T callToRpc(...)
0000000100007118 T execCommand(std::__1::basic_string<...> const&, int&)

The binary was not stripped. Those function names gave away the basic layout right away. ovpnhelper runs a small local HTTP server over /var/run/ovpnhelper_service.sock, sets up routes in GetRoutes(), and has helper functions underneath named callToRpc and execCommand.

Checking Caller Validation

ServerListener::allow_client looked like the function that decides whether a connecting process is allowed to talk to the helper. On macOS, this is where you would expect a root helper to verify the caller's code signature so only the real OpenVPN app can send requests.

I used angr to load the binary and print the ARM64 instructions for allow_client:

import angr

BINARY = "/Library/Frameworks/OVPNHelper.framework/Versions/Current/usr/sbin/ovpnhelper"
project = angr.Project(BINARY, auto_load_libs=False, load_debug_info=False)

block = project.factory.block(0x1000329cc, size=8)
for insn in block.capstone.insns:
    print(f"{insn.address:#x}: {insn.mnemonic} {insn.op_str}")
0x1000329cc: mov w0, #1
0x1000329d0: ret

On ARM64, w0 holds the return value. Putting 1 into w0 and returning is the compiled version of:

bool ServerListener::allow_client(...) {
    return true;
}

It does not check the caller at all. Any local program that connects to the socket is accepted.

Talking HTTP Over the Socket

Looking at GetRoutes() (0x10000797c) showed two HTTP POST routes: /list-apps and /dpc-request.

To test the server from my normal user account, I updated the Python socket script from Part 1 to send a POST /list-apps request with an empty {} JSON body:

import socket

request = (
    b"POST /list-apps HTTP/1.1\r\n"
    b"Host: localhost\r\n"
    b"Content-Type: application/json\r\n"
    b"Content-Length: 2\r\n"
    b"Connection: close\r\n\r\n"
    b"{}"
)

with socket.socket(socket.AF_UNIX, socket.SOCK_STREAM) as conn:
    conn.settimeout(10)
    conn.connect("/var/run/ovpnhelper_service.sock")
    conn.sendall(request)
    response = b"".join(iter(lambda: conn.recv(4096), b"")).decode("utf-8")
    print(response)

The root helper answered with 200 OK and a full JSON list of installed applications and installer receipts, without needing any auth header, token, or app signature. Here is the response trimmed to the OpenVPN entries:

What the Helper Does

/list-apps only reads installed package info, so I moved on to /dpc-request, handled by DPCRequestHandler.

DPC stands for Device Posture Check. When you connect to a corporate VPN, the VPN server can ask the client to check the state of the machine before allowing access. Looking at DPCRequestHandler::DPCRequestHandler() (0x10000db9c), the helper registers six checks:

  1. antivirus checks running processes for antivirus software
  2. disk_encryption checks whether FileVault is enabled
  3. client_info collects basic macOS and host info
  4. certificate looks up client certificates
  5. epki_certificate looks up external PKI certificates
  6. epki_signature signs data using a certificate's private key

The first three check system state and run directly inside the ovpnhelper root process.

The last three need access to the logged-in user's macOS Keychain. Because ovpnhelper runs as a root LaunchDaemon in the background system session, it is separate from the logged-in user's session. To work around that, the helper spawns a child process inside the target user's session using launchctl asuser <uid>.

Decompiling /dpc-request with angr

To trace how /dpc-request processes input, I wrote a short angr script to build a control-flow graph and decompile individual functions into C-like pseudocode:

import angr

def decompile_function(binary_path: str, start: int, end: int) -> str:
    # Fresh Project per function avoids CFG truncation on larger C++ methods
    project = angr.Project(binary_path, auto_load_libs=False, load_debug_info=False)
    cfg = project.analyses.CFGFast(
        regions=[(start, end)],
        function_starts=[start],
        start_at_entry=False,
        normalize=True,
        data_references=True,
        resolve_indirect_jumps=True,
    )
    func = cfg.kb.functions[start]
    dec = project.analyses.Decompiler(func, cfg=cfg.model)
    return dec.codegen.text

validateJSON and validateRequest verify that the request body is valid JSON with a few required header fields:

{
  "ver": "1.0",
  "correlation_id": "request-123",
  "timestamp": 1730000000,
  "user_id": "501"
}

Once a request passes that check, the loop walks the six registered checks and calls processSingleFunction on each entry. When it reaches the certificate checks, it passes the request to callToRpc.

Finding the Bug

Next I decompiled callToRpc (0x100007240) and execCommand (0x100007118).

Here is the relevant section from callToRpc:

// Excerpt from angr decompilation of callToRpc (0x100007240)
Json::StreamWriterBuilder::StreamWriterBuilder(&v11);
...
Json::writeString(&v11, arg_2); // serializes JSON object back to a string
sub_100009dc4(&v12);            // gets path to the current ovpnhelper binary
...
sub_100358d00();                // formats the shell command string
execCommand(&v22, &v3);         // executes the command string

And here is execCommand:

// Excerpt from angr decompilation of execCommand (0x100007118)
v6 = _popen();
if (v6)
{
    while (1)
    {
        if (!_fgets(&v0, 128, v6))
            break;
        std::__1::basic_string<...>::append(v5, &v0, _strlen(&v0));
    }
    v10 = _pclose(v6);
    ...

angr missed the arguments passed into sub_100358d00() and _popen(), so I checked the disassembly around 0x10000742c to see what strings were loaded into registers. Right before calling execCommand, callToRpc loads this template:

launchctl asuser '{}' '{}' --rpc '{}' --rpc-json '{}'

Putting the pseudocode and disassembly together, those two functions are doing the equivalent of:

// Simplified C++ view of callToRpc and execCommand
std::string json_text = Json::writeString(builder, request_json);

std::string command = fmt::format(
    "launchctl asuser '{}' '{}' --rpc '{}' --rpc-json '{}'",
    user_id,      // from request JSON (or current user)
    helper_path,  // /Library/Frameworks/.../ovpnhelper
    rpc_name,     // e.g. "DPC_API::processCertificate"
    json_text     // serialized request JSON
);

FILE* pipe = popen(command.c_str(), "r");

That is the bug.

Json::writeString formats a JSON object as text. Because JSON strings use double quotes ("..."), the serializer escapes double quotes (\"), and leaves single quotes (') untouched. callToRpc then places that JSON string inside single quotes ('...') and hands the whole command string to popen().

popen() passes the string to /bin/sh -c. Even though the command is trying to run launchctl asuser, ovpnhelper is running as root, so /bin/sh starts as root first to parse the command line. If a field in the JSON contains a single quote ('), /bin/sh treats it as the end of the --rpc-json argument and executes whatever comes next as UID 0.

Confirming Root Execution

To verify this on my machine without making lasting changes, I sent a test request from my normal user account (UID 501) that ran ps inside the spawned shell and deleted its temporary output file right after. I left the exploit payload out of this post, and here is what the canary recorded:

PID     PPID    EUID    RUID    COMMAND
22201   647     0       0       sh

PPID 647 is the ovpnhelper daemon from Part 1, and PID 22201 is /bin/sh running with real and effective UID 0.

Protection

To see how newer versions handle this path, I downloaded OpenVPN Connect 3.8.2 (build 6009) and inspected its ARM64 ovpnhelper binary (SHA-256: c3ac312b9eec74f963ae366826c132620b9ccd97edec8192db2bd90967e4a3d2) statically in angr without installing it.

In build 6009, callToRpc removes /bin/sh and popen() from this path. It checks user_id and the handler name against strict regular expressions, passes an argument array directly to posix_spawn, and sends the JSON over stdin:

// Conceptual view of the build 6009 launch path (static analysis only)
// user_id checked against ^[0-9]{1,10}$
// rpc_name checked against ^[A-Za-z_][A-Za-z0-9_:]{0,127}$

const char* argv[] = {
    "/bin/launchctl", "asuser", user_id.c_str(),
    helper_path.c_str(), "--rpc", rpc_name.c_str(), nullptr
};

spawnAndCapture("/bin/launchctl", argv, json_text); // json_text written to stdin

Without a shell parsing the command string, quotes inside the JSON are just plain bytes on stdin.

More generally, root helpers on macOS have two boundaries to protect. First, the helper should verify who is connecting using system-provided caller identity and code-signing checks instead of returning true for every local socket client. Second, privileged code should avoid passing client data into popen() or system() when posix_spawn can run the target binary directly.

Wrapping up

In Part 1, basic enumeration commands and a short Python script showed that my user account could connect to OpenVPN's root helper over /var/run/ovpnhelper_service.sock. In Part 2, nm and angr showed what sat behind that socket: an unauthenticated local HTTP server that passed JSON input into a single-quoted popen() command running as root.
