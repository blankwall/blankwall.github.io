Part 1: Recon — Finding Root Helpers on macOS

November 16, 2026

Sitting in a hotel room with an older Mac I had been travelling with, I wondered what I would look at if I wanted to get root access. This series follows that investigation, starting with identifying root helpers and their communication endpoints. Root on macOS is not all-powerful. Additional protections include System Integrity Protection and Transparency, Consent, and Control, which I’ll cover separately.

Test Environment

This investigation was performed on an Apple Silicon Mac running macOS 15.3 (build 24D60), with OpenVPN Connect 3.6.0 (build 5410) installed. The ovpnhelper binary was associated with installer receipts for 3.6.0-5410. I did not establish a separate helper-specific version number.

These observations apply to that installation, not every OpenVPN or macOS version.

Identifying Root Applications

First order of business was to look in common places to identify potential root applications that may contain vulnerabilities. I wanted to identify third-party applications that were installed on my system and how I could communicate with them.

I listed running processes and looked for an effective UID of 0. Here, ruid is the real UID and uid is the effective UID. I was interested in processes whose effective UID was 0.

ps -axo pid=,ppid=,ruid=,uid=,comm=

One process of interest this exposed:

  647     1     0     0 /Library/Frameworks/OVPNHelper.framework/Versions/Current/usr/sbin/ovpnhelper

Next I checked locally installed LaunchDaemons. Their plist files identify the executable and any configured user. System LaunchDaemons default to root unless another user is specified.

ls -lha  /Library/LaunchDaemons/
-rw-r--r--   1 root  wheel   586B Dec 13  2024 org.openvpn.client.plist
-rw-r--r--   1 root  wheel   485B Dec 13  2024 org.openvpn.helper.plist

The plist omits the UserName field, meaning this system daemon is configured to launch as root.

plutil -p /Library/LaunchDaemons/org.openvpn.helper.plist
{
  "KeepAlive" => 1
  "Label" => "org.openvpn.helper"
  "ProgramArguments" => [
    0 => "/Library/Frameworks/OVPNHelper.framework/Versions/Current/usr/sbin/ovpnhelper"
  ]
  "RunAtLoad" => 1
  "SessionCreate" => 1
}

I checked the helper’s launchd registration:

launchctl print system/org.openvpn.helper

excerpt:

system/org.openvpn.helper = {
    path = /Library/LaunchDaemons/org.openvpn.helper.plist
    type = LaunchDaemon
    state = running
    program = /Library/Frameworks/OVPNHelper.framework/Versions/Current/usr/sbin/ovpnhelper
    domain = system
    pid = 647
    ...
}

This confirmed the executable and running process. It did not show declared Mach services or sockets. A daemon can create its own communication endpoint after starting, so their absence here did not rule out communication.

Next I listed /var/run/, looking for root-owned Unix sockets that might belong to these processes.

ls -lha /var/run/
srwxrwxrwx   1 root         daemon          0B Oct  3 11:50 ovpnhelper_service.sock

The socket name suggested a connection to OpenVPN. The socket's filesystem permissions suggested that an unprivileged process could attempt a connection, but the server's own authorization logic remained unknown. Next I wanted to see whether my ordinary user account could connect.

Scripting

I consolidated these checks into a small throwaway tool to automate the enumeration. root_helpers.py collects root processes, LaunchDaemon configurations, and communication endpoints worth investigating. Below is a condensed excerpt showing its output for OpenVPN.

$ python3 root_helpers.py

OpenVPN helper
  Executable: /Library/Frameworks/OVPNHelper.framework/
              Versions/Current/usr/sbin/ovpnhelper
  Observed running as root
  File permissions: -rwxr-xr-x, root-owned
  LaunchDaemon: org.openvpn.helper

Selected root-owned socket node:
  srwxrwxrwx /var/run/ovpnhelper_service.sock
  Not yet attributed to a process by this inventory

Connecting

import socket
import struct

with socket.socket(socket.AF_UNIX, socket.SOCK_STREAM) as connection:
    connection.settimeout(3)
    connection.connect("/var/run/ovpnhelper_service.sock")
    # macOS: SOL_LOCAL = 0, LOCAL_PEERPID = 2
    peer_pid = struct.unpack("i", connection.getsockopt(0, 2, 4))[0]
    print(f"Connected to PID {peer_pid}; no request sent.")

The snippet printed Connected to PID 647; no request sent. Success. I then checked the process behind that PID:

ps -p 647 -o pid=,uid=,comm=
  647     0 /Library/Frameworks/OVPNHelper.framework/Versions/Current/usr/sbin/ovpnhelper

My ordinary-user Python process could connect to the socket. The peer-PID check confirmed the endpoint belonged to the OpenVPN helper running as root. Connecting did not elevate my process or prove that privileged requests would succeed. Next I needed to understand what requests the helper accepted and how it handled them. I will dig into that in the next blog in this series.

Protection

Allowing an ordinary user to connect is not necessarily a vulnerability. A privileged helper exists to perform work for less-privileged clients. The important question is how it identifies callers and authorizes their requests. System-provided caller identity and code-signing requirements can help restrict access, but the helper still needs to validate each operation and its inputs.

Wrapping up

I had identified a root-owned helper, discovered its communication socket, and established a connection from an ordinary user account.

That wasn't a vulnerability by itself. It was an attack surface worth investigating.

In Part 2, I'll reverse engineer the helper's communication protocol, trace how it handles incoming requests, and demonstrate the privilege boundary failure that ultimately allowed command execution as root.
